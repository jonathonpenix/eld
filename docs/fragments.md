# Fragments in eld

## What is a Fragment?

A Fragment is the minimum unit of content the linker operates on. Every piece of data that ends up in the output binary — code, data, padding, GOT entries, trampolines — is held in a Fragment.

Input sections from object files are read and stored as fragments. The linker then lays out, relocates, and emits those fragments in order to produce the output. Some fragments are generated by the linker itself (stubs, GOT/PLT entries, fill padding) rather than read from input files.

The fragment model exists to support operations that are hard to do on raw section data:

- **Merging**: SHF_MERGE sections deduplicate strings across inputs.
- **Relaxation**: Instructions can be rewritten or deleted with correct tracking of all symbols and relocations that were pointing into the region.
- **Linker-generated content**: Stubs, GOT slots, PLT entries, and alignment fills can be inserted alongside input content without special-casing the layout engine.
- **Exception frames**: `.eh_frame` CIEs and FDEs need to be processed, deduplicated, and re-emitted with updated offsets.

## Fragment Hierarchy

```
Fragment (base)
├── RegionFragment          — read-only region from an input file
├── RegionFragmentEx        — mutable region supporting relaxation
├── FillFragment            — linker-generated fill/padding
├── StringFragment          — a single null-terminated string
├── MergeStringFragment     — all mergeable strings from a SHF_MERGE|SHF_STRINGS section
├── EhFrameFragment         — .eh_frame data (CIEs and FDEs)
├── Stub                    — linker-generated trampoline for out-of-range branches
├── GOT                     — a Global Offset Table entry
├── PLT                     — a Procedure Linkage Table entry
├── BuildIDFragment         — .note.gnu.build-id content
├── OutputSectDataFragment  — content from linker script DATA commands
└── ... (hash tables, versioning, SFrame, etc.)
```

All fragments have:

- A `Kind` (the enum discriminator for `dyn_cast`/`isa`).
- A pointer to the `ELFSection` that owns them.
- An `UnalignedOffset` — their position in the section before alignment padding is added.
- An `Alignment` requirement.

---

## Offsets and Addresses

A fragment's final byte offset within its output section has two parts:

```
getOffset() = UnalignedOffset + paddingSize()
```

`paddingSize()` is computed on demand from the fragment's alignment requirement and the output section's current address. A fragment's virtual address is therefore:

```
getAddr() = outputSection->addr() + getOffset()
```

Padding is not a separate fragment — it is implicit in the gap between `UnalignedOffset` and the aligned offset. The layout engine assigns `UnalignedOffset` by iterating fragments in order; alignment is resolved automatically at address calculation time.

## RegionFragment and RegionFragmentEx

These are the two fragment types you will encounter most frequently.

**RegionFragment** holds a `StringRef` into the input file's memory. It is immutable. The linker reads code and data sections from input object files into `RegionFragment`s.

**RegionFragmentEx** holds a mutable byte buffer. It supports three operations used during relaxation:

- `replaceInstruction(offset, reloc, newBytes, size)` — overwrites bytes at `offset` with `newBytes`.
- `deleteInstruction(offset, size)` — removes `size` bytes starting at `offset`, shrinking the fragment. All relocations and symbols that pointed past the deletion point have their offsets decremented by `size`.
- `addRequiredNops(offset, count)` — inserts NOP instructions (used during alignment relaxation).

Because `RegionFragmentEx` tracks the symbols and relocations that reference it, deletions stay consistent: a relocation at offset 100 that pointed into code after a 4-byte deletion at offset 80 will automatically be adjusted to offset 96.

---

## FragmentRef

A `FragmentRef` is a (Fragment *, offset) pair. It is how symbols and relocations record their target locations. Rather than storing a raw virtual address, they store a reference to the fragment and an offset within it. This survives relaxation correctly: as `deleteInstruction` adjusts offsets in a `RegionFragmentEx`, any `FragmentRef` pointing into that fragment is updated.

Key methods:

- `getOutputOffset()` — the byte offset of this reference within the output section. For merge fragments and `.eh_frame`, this translates the input offset to the post-deduplication output offset.
- `getOutputELFSection()` — the output section this reference lands in.

---

## Fragments and Sections

An `ELFSection` owns a list of fragments (`SmallVector<Fragment *, 0>`). For a typical input section there is one `RegionFragment` (or `RegionFragmentEx`) per section; for merged or exception-frame sections there may be only one fragment for the entire section that internally manages multiple pieces.

The output layout is determined by the order fragments appear in the output section's fragment list, which corresponds to the order input sections were matched by the linker script.

---

## Linker-Generated Fragments

Not all fragments come from input files. The linker inserts fragments for:

- **Stubs** (branch islands): when a branch target is out of range, the RISCV (or other) backend creates a `Stub` fragment containing a trampoline and inserts it near the call site.
- **GOT/PLT**: symbol accesses that require runtime fixups generate `GOT` and `PLT` entries as fragments in the `.got` and `.plt` output sections.
- **Fill and alignment**: `FillFragment` is inserted to satisfy alignment constraints or `FILL()` commands in the linker script.
- **Linker script `DATA` commands**: `LONG`, `QUAD`, etc. produce `OutputSectDataFragment`s.

## Fragment Lifecycle

```
1. Read from input   — ELFReader creates RegionFragment / MergeStringFragment
                       / EhFrameFragment from input file data.

2. IR building       — Fragments are added to ELFSection fragment lists.
                       Symbols and relocations record FragmentRefs.

3. Symbol resolution — FragmentRefs are used to compute symbol values.
                       Merge string deduplication assigns output offsets.

4. Relaxation        — RegionFragmentEx fragments are modified via
                       replaceInstruction / deleteInstruction. Symbols
                       and relocations tracking into the fragment are
                       updated automatically.

5. Layout            — The layout engine iterates fragments in order,
                       assigning UnalignedOffset to each. Addresses
                       are derived on demand.

6. Relocation apply  — The relocator uses FragmentRef to find the
                       target bytes, computes the relocation value, and
                       patches the fragment's data.

7. Emission          — emit() is called on each fragment in order.
                       The fragment writes its bytes (and any alignment
                       padding) to the output memory region.
```

## Relaxation and RegionFragmentEx in Detail

The RISCV backend uses `RegionFragmentEx` extensively. As an example, call relaxation collapses a 8-byte `auipc + jalr` pair into a 4-byte `jal` or a 2-byte `c.j`:

```cpp
// Replace the first instruction with jal.
region->replaceInstruction(offset, reloc, &jal_instr, 4);
reloc->setTargetData(jal_instr);
reloc->setType(R_RISCV_JAL);

// Delete the trailing 4 bytes (the now-redundant jalr).
relaxDeleteBytes("RISCV_CALL", *region, offset + 4, 4, sym->name());
```

`relaxDeleteBytes` is a thin wrapper around `deleteInstruction` that also reports the savings. After the deletion, the fragment is 4 bytes shorter and all subsequent relocations in the fragment have had their offsets decremented by 4.

GOT load relaxation follows the same pattern, converting an `auipc + lw` GOT indirection into either `auipc + addi` (for relative symbols) or a pair of `addi` / `c.li` (for small absolute symbols).

## MergeStringFragment

A `MergeStringFragment` covers an entire `SHF_MERGE | SHF_STRINGS` input section. Internally it holds a vector of `MergeableString` entries, one per null-terminated string in the section. During symbol resolution, the linker deduplicates across all merge fragments for the same output section and assigns each unique string an output offset. Strings that are suffixes of longer strings can also be folded.

Because the output offset differs from the input offset, `FragmentRef::getOutputOffset()` handles the translation for symbols and relocations that point into a merge section.

---

## EhFrameFragment

An `EhFrameFragment` stores the raw `.eh_frame` data from one input section, plus a parsed vector of `EhFramePiece` entries (each a CIE or FDE with its associated relocation). The linker deduplicates CIEs across inputs: multiple FDEs that reference the same CIE encoding share one output CIE. Output offsets for each piece are assigned during layout and translated on demand via `FragmentRef::getOutputOffset()`.
